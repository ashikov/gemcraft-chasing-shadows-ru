# Windows-инсталлятор: private preview

Это локальный офлайн-инструмент, не публичный релиз. Он не содержит оригинальный
или готовый SWF. Пользователь выбирает принадлежащую ему установку, проверяет
точную цель и SHA и подтверждает запись. Игра автоматически не запускается.

GUI `installer_gui.py` использует Tkinter и общий backend `windows_installer.py`.
Текущая версия обозначается первыми символами `expected_candidate_sha256` из
`translations/build-manifest.json`; исходники GUI менять при новом переводе не нужно.
Сборка кандидата использует `localization_project.build_project()`, оригинал
пользователя или проверенный оригинальный backup и закреплённый Alegreya.

Поддерживаются оригинал → перевод, известный перевод A → B, повторная установка
и восстановление оригинала. Неизвестный SWF, повреждённый backup, отсутствующий
или противоречивый manifest блокируют операцию. Откат SWF не откатывает прогресс.
Старые backup и manifest сохраняются. Исторические патчи, установленные другими
инструментами, без подходящих проверенных данных этого инсталлятора автоматически
не импортируются: неизвестный файл требует отдельного разбора.

Данные инсталлятора находятся в отдельном пользовательском каталоге
`%LOCALAPPDATA%\GemCraftRUInstaller`, вне Steam и распакованных ресурсов приложения.
Точный путь backup показывается в результате операции. При недостатке прав
операция останавливается; пользователь может явно запустить EXE от администратора.
Автоматического повышения прав, служб и изменений реестра нет.

## Нативная сборка следующей версии

Нужны Windows x64, Windows Python 3.11+ с Tkinter, свежий согласованный `main`,
проверенный оригинал своей игры и локальный закреплённый TTF по README.
Зависимости заранее установите в отдельное окружение; для полностью офлайн-сборки
предварительно подготовьте wheelhouse. Во время установки доступ к сети не нужен.

```powershell
py -3.11 -m venv .venv-installer
.\.venv-installer\Scripts\python -m pip install -r requirements-installer.txt
.\.venv-installer\Scripts\python build_windows_installer.py `
  --source 'D:\OwnedOriginal\gc-cs-steam.swf' `
  --font 'D:\Fonts\Alegreya[wght].ttf' `
  --output 'output\windows-installer'
```

Сценарий валидирует каталог, планы и provenance, формирует стабильный allowlist
ресурсов с SHA каждого файла, дважды собирает кандидат штатным путём и только
затем запускает PyInstaller. Неверный SHA кандидата или несовместимый renderer
останавливает сборку. Pillow 12.3.0 должен иметь версии JPEG/FreeType, закреплённые
планом карты; совпадение Python-пакета само по себе этого не гарантирует.
Сборку нужно выполнять нативно: PyInstaller не является cross compiler.

Результат: `GemCraft-RU-<SHA prefix>.exe`, входной inventory и SHA EXE в выбранном
каталоге. Внутри EXE — инструменты Python, собственный каталог и планы, TTF и
OFL/copyright/provenance Alegreya. Ресурсы находятся относительно `__file__`,
поэтому текущий рабочий каталог не влияет на поиск. Временные SWF и двуязычный
workspace уничтожаются после сборки и не включаются в EXE.

Повторяйте эту команду после обновления переводов и manifest; ручная замена SHA
в GUI не требуется. Детерминированность списка и содержимого входов проверяется
синтетическим тестом. Битовое совпадение EXE между разными Python, Windows,
версиями упаковщика и toolchain не гарантируется; для проверки повторите сборку
дважды в одном окружении и сравните `.sha256` и `-inputs.json`.

## Проверка preview

Запускайте EXE только на изолированной копии структуры файлов. Проверьте открытие
GUI двойным кликом из другого cwd, пути с пробелами и кириллицей, original → A,
A → B, повторную установку, restore и отказы при повреждениях. Не запускайте игру
ради файловой проверки. Настоящая Steam-установка, сохранения и Steam Cloud
в этот этап не входят.

Linux CI проверяет backend и allowlist на синтетических данных; эти проверки
не доказывают работоспособность нативного Tkinter, Pillow или PyInstaller на
Windows. Факт успешной сборки/запуска EXE должен фиксироваться отдельно.
Публичная публикация EXE, игровые материалы, Release и merge не разрешены.
Условия и ограничения прав описаны в [legal.md](legal.md).

## Свидетельства текущего этапа

Linux/WSL: синтетические операции A → B → original, повторная установка,
повреждения, гонки цели/сохранений, отказ staging при недостатке прав,
целостность посторонних файлов и повторяемость allowlist проверены тестами.
Два staging-прохода реальных закреплённых ресурсов дали одинаковые 72 SHA;
проверены font provenance, каталог и все планы. Независимое ревью выявило
и устранило self-block EXE/onefile bootloader в проверке процессов.

Нативный Windows Python в доступной системе отсутствует: найден только
Microsoft Store alias, `python --version` завершается ошибкой. Поэтому EXE
не создан и GUI не запущен; нативная упаковка, renderer и интерфейс на Windows
остаются непроверенными. В CI добавлен Windows job с синтетическими backend
транзакциями и smoke проверки Toolhelp, без игры и пользовательских данных.

После аварийного завершения остаётся `operation.lock` в каталоге установки
внутри данных инсталлятора. Он блокирует повторную запись. Перед удалением
такого lock нужно проверить отсутствие процессов всех версий установщика;
backup и журналы удалять не нужно. Автоматическое снятие чужого lock запрещено.

Первый CI-прогон preview подтвердил Linux suite (1492 passed, один Windows-only
smoke skipped) и Windows job (26 passed, один symlink-тест deselected, поскольку
ему нужны отдельные Windows privileges). Windows job действительно исполнил
Toolhelp smoke. Это не сборка EXE и не проверка GUI или Windows renderer.

## Проверка упаковки после ревью PR #39

Python-модули больше не копируются в resources по wildcard. PyInstaller строит
граф импортов от `installer_gui.py`, включая обычные импорты внутри функций.
Pillow и fontTools собираются с их дополнительными модулями через collect-all.
Как данные передаются только каталог, manifest, перечисленные планы и
TTF/OFL/provenance. `secret.py` в корне не входит в staging; отдельная проверка
упакованного приложения проверяет отсутствие такого модуля в архиве.

Windows job `windows-packaging-smoke` собирает onefile тем же генератором
команды PyInstaller, но с отдельным диагностическим entry point и исключительно
синтетическими данными. EXE запускается из другой папки с пробелами и кириллицей,
проверяет bundled resource, runtime-импорты, Pillow/fontTools и создание окна
настоящего GUI с фиктивным backend. При отсутствии доступного desktop/Tk
GUI-проверка явно помечается пропущенной с причиной. EXE, входы и отчёт остаются
во временной директории runner и не загружаются в artifacts. Steam, сохранения,
приватные переводы и оригинальный SWF этот job не читает и не упаковывает.

Это синтетическая проверка упаковщика, а не production EXE. На пользовательской
Windows-машине ещё нужны штатная сборка с собственным проверенным оригиналом,
проверка закреплённого renderer и production SHA, запуск production GUI и
операции на изолированной копии. PR остаётся Draft; Steam-установка и игра
в эти проверки не входят.
